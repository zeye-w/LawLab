# LawLab P2 · 统一虚构法律案例库（第一批）

## 交付边界

P2 的重点是打破已有模块中的各自维护的“同一案故事”。本次以一个 **完全虚构** 的设备采购合同纠纷为示例，提供可读取的教学资料摘录，并在五个页面共用同一 Registry：

- `#casebook`：独立案例资料库，查看 7 份教学文书、双方立场、待证事实、候选证据和关联节点。
- `#evidence`、`#timeline`、`#reasoning`、`#court`：同一套案件资料包以原生 `details` 折叠展示，便于对照。
- `src/data/cases.ts` 的 `EVIDENCE`（原 4 个 ID）已由 Registry 转为兼容只读视图。
- `src/lib/timeline.ts` 的 `INITIAL_EVENTS`（原 6 个 ID）由 Registry 导出；**localStorage 原 Key `lawlab.timeline.v1` 未变化，已有自定义事件不会自动被替换或清空**。
- 法律题目、预设双方庭审策略、用户记忆卡等保持原有交互，不把固定选择题答复当作对新案例事实的法律裁判。

       ↙       ↓       ↘
data/cases.ts   lib/timeline.ts   components/CaseDossier.tsx

同一案的合同金额 60,000 元、预付金额 20,000 元、交付期限 2025-04-01 都只是教学设定。双方当事人以及所有文书并非真实存在。聊天节选有歧义，仓储发运登记也不等于完成交付，系统不得自动据此认定延期合意、付款到账、违约或胜诉概率。

## 数据与验证

`CaseDocument` 的文书原始教学摘录、编写身份、日期、真实性局限、证据和时间线关系均单独记录。`CasePosition` 连接当事人陈述与具体待证事实。规范化 ID 采用 `case:cn:equipment-sale-demo-001:document:* / evidence:* / event:* / fact:*` 等稳定前缀。

自动校验会阻断：重复实体 ID、无效日期、空白摘录与审查局限、缺少关联的文书、悬空事件或证据引用、文书重复关联、超出案例名单的当事人及不存在的争议事实。所有验证都只保证程序化数据一致性，**无法证实案卷真实性或法律适用**。

## 数据迁移策略与风险

现存的 `lawlab.timeline.v1` 可包含用户编辑数据，因此不清除、不重命名、不强制回填。首次运行的新浏览器会读取 Registry 生成的事件；曾访问的用户仍显示此前保存的条目。后续若需要提供新版演示时间线，应由用户显式选择“载入示例”，并在覆盖或合并前确认。

本轮不上传材料到服务器、不处理真实委托资料，不执行 AI 法律建议，也不通过法条来源的 `pending` 状态臆测有效性。法律概念与法条的人工核验继续单独推进。

## 验收流程

1. 访问 `#casebook`，展开七份文书并查看各自的候选证据/事件链接。
2. 访问 `#court`、`#reasoning`、`#evidence`、`#timeline`，确认同一案例摘要和资料文书都能打开。
3. 在证据链选择“银行转账记录”，仍应只显示可能关联付款的关系，而不自动将付款事实标记为真实。
4. 时间线原事件、CSV 导出、增加用户事件及历史 `localStorage` 都保持原行为；在旧浏览器需允许保存的旧资料不被替换。
5. 运行 `npm test`、`npm run build` 和 Wrangler dry-run；PR Preview 做桌面与手机阅读及键盘交互验收。
